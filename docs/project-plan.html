SF Data Migration Tool — Agentic Layer: Project Plan and Tool Requirements

1. Tool requirements

ToolAccess neededJustification
Amazon Bedrock Model access in us-east-1 (N. Virginia) for two models: anthropic.claude-sonnet-5 (relationship agent) and anthropic.claude-haiku-4-5 (repair agent) Runs both agents and is the only new capability the project needs. Sonnet 5 handles the relationship reasoning and Haiku 4.5 the narrower repair task at lower cost; both model IDs are application configuration, so either can be changed without a rebuild. Both models have been confirmed reachable in us-east-1 and are not served in us-east-2 or us-west-2, which is what fixes the region for the project.
Bedrock IAM permissions bedrock:InvokeModel, bedrock:InvokeModelWithResponseStream, bedrock:Converse, bedrock:ConverseStream — scoped to the two foundation-model ARNs in us-east-1 How the application calls the models. In-region access in us-east-1 keeps this to a single pair of ARNs. If cross-region failover is wanted later, the same actions can be extended to the US geo inference profile, which additionally requires naming the underlying foundation-model ARNs in each member region — not needed for the initial build.
EC2 One general-purpose Linux instance in us-east-1 — 2 vCPU / 8 GB as a starting point, right-sized after the first client run Hosts the API, the wizard and the migration worker. Migrations run for hours and hold staged data in flight, so they need a persistent instance rather than a request-scoped process. Local disk sized to the largest expected extract, since the staged source data is held on the instance.
S3 One private bucket in us-east-1, public access blocked, default encryption on, versioning on Holds the checkpoint that makes a migration resumable: the map of source records already written to the destination, the batch state and the resolved mapping configuration. A session interrupted part way through an object continues from that record rather than restarting, and a replacement instance can recover prior runs from the bucket. Extracted source data is deliberately not stored here — it stays on the instance, so the bucket holds kilobytes of progress rather than gigabytes of client data. Versioning gives checkpoint history; same region as the instance avoids cross-region transfer charges and latency on every save.
EC2 instance IAM role s3:GetObject, s3:PutObject, s3:DeleteObject on that bucket's prefix, plus s3:ListBucket and s3:GetBucketVersioning on the bucket, plus the Bedrock actions above Lets the instance reach the bucket and the models without long-lived access keys on disk. Delete and list are needed to retire a completed session's checkpoint and to enumerate recoverable sessions.
CloudWatch Log group for the application; Bedrock model invocation logging enabled Makes token spend attributable per migration and gives us run diagnostics without shell access to the instance.
Cost. EC2 is ordinary hosting for the tool and is sized by data volume, since the staged extract sits on its disk. S3 is negligible: checkpoints are progress records rather than data, so a bucket serving many migrations stays in the kilobytes-to-megabytes range. Bedrock is usage-based and driven by schema size rather than data volume, because the agents read field definitions and dependency graphs, never records — order of magnitude, under one hundred dollars for the whole build and under two dollars per migration, held there by a per-session token cap, per-call token logging, and a budget alarm.

2. Time estimate

  • Total: four to five weeks, one engineer already familiar with this codebase, stages worked in order.
  • ≈3 weeks — agent evaluable against real client data, still read-only.
  • ≈4 weeks — agent permitted to write configuration, with revert in place.
  • Excludes the wait for AWS access, which is the critical path ahead of every number here.
  • Stage 5 holds the widest range as the only empirical stage; re-forecast at the end of phase 1.
  • Phases 1 to 3 execute nothing during a live migration and can absorb slippage around client delivery. Stage 9 is presentation only and can be dropped from the first release.
