SF Data Migration Tool — Selectively Agentic Architecture

1. Division of responsibility

The tool stays a deterministic ETL pipeline: source data is extracted in full to our side, then transformed and loaded into Salesforce. Agents are applied selectively, to the two problems that deterministic rules have not solved — getting relationships between objects right, and recovering from load errors. Everything else, including extraction, transformation, loading and ordering, runs exactly as it does today.

Where they are applied, the agents act as a configuration layer: they read system state, decide what the pipeline needs in order to move related data correctly, and then build that configuration themselves — which the pipeline executes exactly as it executes hand-written configuration today.

  1. Only the ETL touches data. Agents read schema, dependency graphs and error summaries. They never read record payloads in bulk, never write to Salesforce, and never modify staged files.
  2. Humans own field-to-field mapping. Choosing that a source field belongs in a particular Salesforce field remains a human decision, supported by the existing auto-suggest.
  3. Agents own relationship correctness and error repair, end to end. Identifier remapping, identifier maps, load ordering, missing parents, and post-load failures. They do not hand a list of problems back to an engineer to wire up — they wire it up, and report what they did. This is the work that is currently manual, iterative, and the main source of failed runs.
  4. Escalate only what cannot be fixed safely. Anything inside the bounded remedy set is resolved autonomously. A decision that genuinely needs human judgement — a required parent that is out of scope, an ambiguous default — is raised as a blocker instead of guessed at.
  5. Every change is validated before it is written. The agent's work is checked against the live Salesforce describe and an allow-list of transform functions. Anything that fails validation is discarded rather than applied, and everything applied is recorded and reversible.
  6. Staged, not streaming. All selected source data lands on our side before any transform runs, so repair and retry operate on local data and never re-query the source system.
  7. Degrades to today's behaviour. If Bedrock is unavailable the agent path is skipped and the pipeline runs unchanged. No model call sits on a data-integrity critical path.

Inside step 2 — how the Relationship Agent works

Step 2 is the substance of the design-time half, so it is worth expanding. It proceeds in five passes, each building on the last. The first four work out what is wrong; the fifth is the one that matters operationally, because the agent fixes it rather than reporting it.

  1. Read both sides of the relationship. On the source side, every field carries a type, and reference fields additionally carry the table they point at — a record's owner field declares that it points at the user table. On the destination side, the Salesforce describe declares which fields are lookups and which objects each lookup accepts. These two facts, put side by side, are what makes dependency discovery possible without reading a single record.
  2. Pair references into dependency edges. For each source reference field, the agent asks whether the table it points at is also part of this migration, and if so which Salesforce object it becomes. When the answer is yes, that is a dependency edge: the child cannot be loaded correctly until the parent exists. When the answer is no, it is a missing parent — the reference has nothing to resolve against, and it is recorded as a notice whose severity depends on whether the destination field is required.
  3. Derive the load order from the edges. The set of edges forms a graph, and the graph is sorted so that every parent loads before anything that points at it. This sort is deterministic and stays in code — the agent's job is to make sure the graph is complete and correct, particularly that no parent is missing from the selection, because a sort over an incomplete graph produces a confidently wrong order.
  4. Find the edge cases ordering cannot express. Correct sequencing alone does not make a relationship work. The child mapping must also carry a resolution step that turns the source identifier into the parent's new Salesforce identifier, pointed at the right identifier map — and some shapes cannot be sequenced at all: a record pointing at its own object, two objects pointing at each other, a lookup that accepts several object types, a parent that sits outside the migration's scope. The agent identifies each of these and selects a remedy from the fixed set in section 5.3.
  5. Wire the remedy into the pipeline. This is the pass that distinguishes the agent from a linter. It does not return a list of things for an engineer to configure — it performs the configuration, then reports what it did. Concretely, it registers the identifier map that the parent mapping will populate during load and attaches the matching lookup transform to the child field, so the child resolves against the parent's new Salesforce identifiers. It pulls a missing parent into the run when the reference cannot work without it. It splits a self-reference or a mutual reference into an insert pass and a follow-up pass that fills the reference once identifiers exist. It writes the resolved parent-first order onto the mappings. It sets a constant or default where a reference points outside scope and a safe default exists. Everything it writes is ordinary pipeline configuration of a kind an engineer would otherwise hand-author, and it is validated against the live Salesforce schema before being saved.

What comes out of step 2 is therefore a configured migration plus a change log, not a to-do list. Step 3 is human oversight of work already done: every item can be inspected and reverted individually, and the only things left genuinely outstanding are the blockers the agent deliberately refused to guess at — a required parent nobody selected, a default with no safe answer. Section 5 covers what it can detect and why that set is deliberately not fixed.

Why these three positions and no others. Step 2 is where a mistake costs nothing to fix, because no data has moved. Step 4 is the last moment at which we can still refuse to start. Step 11 is the only point where Salesforce has told us something we could not have known in advance. Anywhere else would place the model between the data and the destination, which the first design rule forbids.

3. How the agent is connected

3.1 Runtime

Each agent is a bounded tool-use loop against the Bedrock Converse API. The model is given a role, a task, and a set of tools; it calls tools to gather facts, then terminates by calling a single submission tool that carries its conclusion. There is no framework in between — the loop is small, and keeping it small is what lets us validate between every turn.

Deployment is a thin service module in the existing FastAPI application. Credentials are resolved server-side and held outside the model's reach: they are captured by the tool executors, never declared in a tool's input schema, so the model can neither see them nor supply them.

3.2 Tools are adapters over logic we already have

This is the reason the agentic layer is a small build rather than a rewrite. The analysis capability already exists in the compatibility engine and is already tested in production runs. The agent does not reimplement any of it — it decides what to inspect and what to conclude.

ToolExisting capability behind itWhat it gives the agent
List source fieldsSource provider field discoveryField names, data types, and which table each reference field points at
List destination fieldsSalesforce describe wrapperType, length, required, createable, lookup targets, picklist values
Suggest mappingDeterministic auto-suggestA name-and-type draft to reason from rather than starting blank
Check typeType coercion engineWhether a pair is compatible, and which transform closes the gap
Resolve orderDependency resolverTopological order, edges, cycles, and missing parents
Check compatibilityCompatibility reportCurrent blockers: unset required fields, raw reference copies, picklist gaps
Submit resolution—The single, schema-constrained channel through which the agent's decisions leave the loop and enter validation
One prerequisite refactor. The dependency resolver and the compatibility report currently load mapping configurations from the database. The agent reasons over drafts before it commits anything, so both need to accept in-memory configurations. Without this, working out what to change would require writing speculative state first — which also breaks preview mode, where nothing may be written at all.

3.3 Guardrails

Because the agent applies its own conclusions rather than handing them to a person, the guardrails carry more weight than they would in an advisory design. They are what make autonomy safe: the agent can decide freely, but only within a space where every possible decision is already known to be executable.

  • Fixed transform allow-list. The agent may only configure generic transform functions already registered in the pipeline. Any other function name is rejected — it cannot introduce new executable behaviour, only new configuration of behaviour that already exists and is already tested.
  • Schema verification before write. Every destination field it touches is re-checked against a fresh Salesforce describe. Unknown or non-createable fields are dropped rather than written.
  • Ordering is recomputed, never trusted. Whatever sequence the agent arrives at is discarded, and the deterministic resolver is re-run over the configuration it produced. Its real contribution is making the graph complete — ensuring the parent is in the selection and wired — while the machine decides the order.
  • Bounded execution. Turn cap, token cap, wall-clock cap per session, a capped number of repair attempts per object, and a global feature flag.
  • Everything applied is reversible. Each change is recorded against the session and object that produced it, so a review can revert one item without unpicking the rest.
  • Full audit. Every decision, validation verdict, and applied change is recorded before it takes effect, with token usage attached.

5. Relationship Agent

5.1 The problem it exists to solve

When related records move into Salesforce, Salesforce assigns new identifiers. A child record that pointed at a parent by its source identifier must instead point at the parent's new Salesforce identifier. The pipeline already has the machinery for this — an identifier map populated during load, and a lookup transform that reads it — but somebody has to notice that a given field needs it, register the map under the name the transform will look for, attach the transform to the right field, and ensure the parent loads first.

Today all of that is manual, and it is the single largest cause of failed runs: the symptom appears late — a malformed-identifier error during load, thousands of records in — while the cause is a configuration decision made much earlier. The agent takes over the whole chain, not just the noticing. Detecting the problem and leaving the wiring to a person would keep the expensive half of the work exactly where it is.

5.2 Why the agent generalizes rather than pattern-matching

Identifier remapping is one scenario. It is not the only one, and the important design point is that we are not building a checklist of known cases. Deterministic rule checking is exactly where the current implementation already stops: a rule catches the case its author anticipated, and every new client dataset produces relationship shapes nobody anticipated.

The agent is given the whole relational picture rather than a list of tests to run:

  • The full source field inventory, including which table every reference field targets.
  • The full Salesforce describe for each destination object — lookup targets (including polymorphic targets), required flags, field lengths, and constrained value sets.
  • The complete set of objects selected for this migration, and what each one maps to.
  • The computed dependency graph, with its edges, cycles, and unresolved parents.
  • The naming convention that links an identifier map to the mapping that populates it.

From that surface, the agent reasons about categories of breakage — a reference that will not resolve, an ordering that cannot satisfy a dependency, a value that will not survive the destination's constraints — rather than matching a fixed catalogue. When it encounters a relationship shape none of us anticipated, it can still describe the problem in those terms and fix it, because the fix is assembled from a small, fixed set of moves that the pipeline already knows how to execute. Novel problem, familiar remedy: that combination is what lets it act on a case nobody wrote a rule for.

5.3 A bounded set of remedies it applies itself

This is what makes autonomous action on open-ended detection safe. Detection is unbounded; action is not. Whatever the agent concludes, the fix it applies must be composed from these primitives, every one of which is something the pipeline already executes today. The agent is choosing and configuring moves, never inventing them.

RemedyWhat the agent actually writes
Wire an identifier lookupRegisters the identifier map the parent will populate at load time and attaches the lookup transform, pointed at that map, to the child's reference field
Bring a parent into scopeAdds the parent mapping to the run so its identifiers exist to resolve against
Reorder the loadWrites the parent-first order onto the mappings, as computed by the deterministic resolver
Split into two passesConfigures an insert pass without the reference and a follow-up pass that fills it once identifiers exist — for self-references and cycles
Substitute a constant or defaultSets a fixed target for a required reference whose real target is out of scope
Add a value mapBuilds the translation from source vocabulary to the destination's allowed values, read from the describe
Coerce a typeConfigures the transform that reformats or bounds the value so the destination accepts it
Raise a blockerWrites nothing and stops the run with a named remedy — the deliberate choice when no safe automatic fix exists
The last row is as important as the others. An agent that always acts is not trustworthy; one that knows when acting would be a guess is. Refusing to fabricate a parent record or invent a default is treated as a first-class outcome, not a failure to resolve.

5.4 Illustrative scenarios

The following are examples of what this reasoning surface plus this remedy set covers today — deliberately presented as illustrations, not as the definition of the agent's scope.

ScenarioWhat the agent recognisesWhat it does about it
Source identifier copied straight into a lookup field Destination is a lookup; the mapping copies a raw value with no resolution step Registers the identifier map and attaches the lookup transform to that field
Parent object not selected for migration A referenced source table has no mapping in the current selection Pulls the parent into the run and wires the lookup; falls back to a default record where one is safe, and raises a blocker where neither is
Multi-level chain across three or more objects Transitive dependency edges in the graph Wires the lookup at every level and lets the resolver order the whole chain
Self-referencing hierarchy, such as a record naming a parent record of the same type A dependency edge from an object to itself Configures a two-pass load: insert first, then fill the self-reference
Circular dependency between two objects A cycle in the graph, which the resolver cannot order Defers the least critical edge to a second pass so the rest can be ordered, and flags the choice it made
Polymorphic reference with several possible targets A destination lookup that accepts more than one object type Configures a multi-target lookup with a defined precedence order

Junction object joining two others A source table composed almost entirely of reference fields Wires resolution on both sides of the join and places it last in the order

5.5 New scenario classes need no code change

The notice channel between the agent and the interface is deliberately open. A notice carries a severity, a category label, the mapping and field it concerns, a plain-language explanation, and either the change that was made or the decision still required. The category label is not a fixed enumeration, so a relationship problem we have never seen is handled correctly without a deployment: it is resolved and logged if it falls inside the remedy set, or it stops the launch and reaches the person who can decide if it does not.

Compounding benefit. Because every notice is audited with its category, the categories that recur across clients become visible. Those graduate into deterministic checks in the compatibility engine — cheaper, instant, and no model call required. The agent effectively acts as a discovery mechanism that keeps hardening the deterministic layer beneath it.

6. Repair Agent

6.1 What it works from

The loader already extracts unique error messages from Salesforce's failed-record output and returns them per object. The repair agent receives that error summary, the object's mapping configuration, and the destination field metadata. It never sees record data — only error text and schema — which keeps the same data-handling posture as the Relationship Agent.

Salesforce error messages are self-describing enough to reason from, and the same bounded remedy set from the previous section applies. Common classes and their typical resolutions:

Error classTypical resolution
Value in the wrong format for its type, commonly datesReformat with the correct input pattern
Value longer than the destination allowsBound it to the described length
Value outside a restricted value setAdd a value map built from the destination's own allowed values
Malformed identifierA missing resolution step — handed back to relationship logic rather than patched locally
Required field empty on some recordsSupply a default, or escalate as a blocker if no safe default exists
Duplicate detection, permission and access failuresNot repairable by configuration; surfaced to the user without retry

6.2 Why staging makes repair practical

Because every selected record already sits on our side before any transform runs, a repair is cheap: the failed object is re-transformed from local data and re-loaded on its own. The source system is not re-queried, successfully loaded objects are untouched, and the identifier map entries already written remain valid. Repair on a streaming pipeline would mean re-extracting and reasoning about partial state; here it is a local, scoped, repeatable operation.

Stopping conditions. A capped number of repair attempts per object per run. Abort immediately if an attempt does not reduce the failure count, if the error class is on the non-repairable list, or if the same patch has already been tried. A run that exhausts repair finishes in the existing completed-with-errors state with the unresolved errors attached — the agent can improve an outcome but never worsen one.

7. State and interfaces

7.1 New state

One new table records agent activity. Every row captures the session and object it concerns, the agent and phase, a digest of the inputs, the change the agent made, the validation verdict, whether it was applied, the prior value it replaced, the model identifier, and token counts. Because the agent writes rather than suggests, this table is doing three jobs at once: it is the audit trail, the mechanism that makes any individual change reversible, and the cost ledger. It also feeds the scenario-frequency analysis described in section 5.5.

7.2 Existing state the agents depend on

  • Mapping configurations — the only design-time write target. The agent adds transform functions, their parameters, and load priorities to the same structure the wizard already saves; nothing structurally new is introduced, which is why its output needs no special handling downstream.
  • Identifier maps — populated during load, read by lookup transforms. The agent registers them as part of wiring a relationship, always deriving the name from the shared naming helper rather than composing one. Hand-built names are the most common relationship defect in the current process, and the validator checks for exactly this before anything is written.
  • Job and batch records — repair retries reuse the same job identifiers so run history stays coherent and a repaired run reads as one run.

7.3 Interfaces

InterfacePurpose
Resolve endpointTakes the current selection and credential references. Runs the agent, validates its conclusions, writes the resulting configuration, and returns a change log, the outstanding blockers, and token usage.
Preview mode on the same endpointIdentical analysis with the write suppressed. Useful for a first run on an unfamiliar client dataset, and for testing.
Revert endpointTakes a change reference and restores the prior value from the audit record. Reversal is per item, not per run.
Notices endpointServes current relationship notices for the pre-launch banner and the run view.

Interface changes in the web application:

  • An agent action in Step 4 alongside the existing auto-suggest.
  • A change-log panel rather than an approval queue: each item states what was wired, on which field, and why, with a revert control. The default is that the work is done; the user is auditing it, not completing it.
  • A separate, prominent list of blockers the agent declined to guess at — these are the only items that actually need a human decision, and they should not be buried among the changes it already handled.
  • A notice strip on each mapping card, colour-coded by severity, driven by the open-ended notice categories.
  • A repair state on the progress view, so an in-flight repair and its rationale are visible while it happens rather than only in the final error list.

What the estimates assume

End to end this is roughly four to five weeks for one engineer already familiar with this codebase, working the stages in order. Two intermediate points are worth planning against rather than the end date alone: the agent can be evaluated against real client data at the end of stage 5, around two and a half to three weeks, and it is permitted to write configuration at the end of stage 7, around three and a half to four weeks. Repair lands last.

  • Sequential, because each stage depends on the one before it. The exception is stage 9, which is presentation only and can trail the rest or be dropped from the first release without affecting behaviour.
  • Stage 5 carries the widest range because it is the only empirical stage. Everything else is ordinary engineering with a testable finish line; prompt and tool-surface iteration converges when it converges. It is also the stage where the range narrows fastest once work starts, so it is the right place to re-forecast from.
  • Stages 1 to 7 carry no runtime risk and can absorb slippage. None of them execute during a migration, so they can be delivered around live client work rather than blocking it.
  • Excluded: waiting for Bedrock access. Stage 1 measures the build once credentials exist, not the approval that precedes it. Nothing can start without that approval, which makes it the critical path ahead of any of these numbers.
  • Excluded: review cycles that depend on other people. Stage 5 is judged by comparing the agent's change log against hand-wiring on a real dataset, so it assumes an experienced engineer is available to do that comparison.
Autonomy is switched on at stage 7, not stage 5. The agent runs in preview for two stages first, which means we can compare its change log against hand-wiring on real client data before it is permitted to write anything, and the revert path exists before the first write does. Stages 1 to 7 also carry no runtime risk: none of them execute during a migration. Repair is the only component that runs inside a live migration, it arrives last, and it sits behind both a feature flag and its own attempt cap.
